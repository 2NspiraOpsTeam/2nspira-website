# Careers job board

## Runtime and access

The existing vinext website serves `/careers`, `/careers/:id` and `/admin/careers`. Admin API requests validate the website's existing `admin_session` with a fixed, read-only session lookup against the portal's authoritative D1 session tables (`CAREERS_AUTH_DB`). This does not invoke the portal statistics/billing handler. The active, unexpired admin identity must also be listed in `CAREERS_HIRING_EMAILS`; valid non-hiring administrators are denied. Only the two existing Jeffrey administrator identities are configured. Client cookies, absent/invalid sessions, and cross-origin mutations are rejected. The dedicated `CAREERS_DB` contains openings, applicant settings, application snapshots, private document chunks and notification outcomes; it does not share billing or client tables.

Production database: `2nspira-careers`. Preview database: `2nspira-careers-preview`. Both preview deployment scripts replace the production binding with the preview database. Never publish synthetic QA roles or applicant details to production.

## Uploads and privacy

Uploaded documents are PDF only, maximum 3 MiB per document, with server-side extension/type/signature and total body limits. Documents are stored privately in bounded D1 chunks and fetched only through the authenticated Admin API. Downloads use fixed filenames, attachment disposition, no-store, nosniff and a restrictive CSP; PDFs are not embedded in Admin. Signature validation is not malware scanning: treat downloads as untrusted. Contact fields and questionnaire answers are validated, rendered as text, and never included in hiring notification emails. Applicant links accept HTTP(S) only and open as external links.

Applicants acknowledge the published privacy notice. A retention review date is snapshotted per application. **Retention is reviewed manually; there is no automatic deletion promise or scheduled purge.** Pending policy, legal holds and unexpired minimum retention block deletion on the server. Authorized hiring personnel can delete eligible expired records in one conditional database batch after review. Hiring decision history is preserved with each application. Provider/platform backups may have independent retention. Confirm the final privacy policy and retention obligations before collecting real applications.

## Email configuration and semantics

Runtime secrets: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`. The existing send-only Gmail grant was installed and its token exchange verified. `CAREERS_REPLY_TO=hiring@2nspira.com`. Unless `CAREERS_SENDER_VERIFIED=true` and an authorized `CAREERS_FROM_EMAIL` is provided, the MIME omits From and lets Gmail supply its authenticated account identity; do not force an unverified alias. `CAREERS_EMAIL_VERIFIED=true` records the completed controlled external-delivery/reply check described below. Retention and posting approval remain independent publication gates. `PORTAL_URL` remains the website login proxy target, but Careers authorization uses the authoritative session lookup. No credentials are committed; do not use fake QA credentials on a hosted deployment.

An accepted application and two outbox entries are committed atomically. Applicant email confirms receipt, not hiring or interview, and includes role title, UTC submission date, application reference and hiring contact. It is created only after the application and attachments are saved. Résumés, cover letters and questionnaire responses are never included. The designated hiring contact receives a sign-in link/reference, not application contents or attachments. Each mail entry is claimed before sending. Safe pre-send failures/provider rejections remain pending and can be retried from Admin; uncertain send outcomes remain unknown/sending and are not automatically resent. `sent` means provider acceptance, not verified inbox delivery. Review provider evidence before resolving uncertain outcomes. Publication requires configured credentials plus an explicit external-delivery/reply verification flag. Set that flag only after controlled inbox evidence is recorded; the current flag is true based on the controlled check below. Credential presence and a successful OAuth exchange alone do not prove delivery.

## Reliability

Client in-flight lock and server idempotency key/hash prevent duplicate creation and email on same-content retries. Different content under a previously accepted key is rejected. Opening revisions guard simultaneous edits and stale questionnaires. Submission commits condition on the opening still being published at the same revision. Closing removes the public role and rejects new applications, preserving existing candidates and questionnaire snapshots.

Per-hour hashed network identifiers rate-limit public submissions. No raw IP is stored. PDF content is not logged. SQL is parameterized. Application API and downloads are private/no-store/noindex. Admin HTML contains no candidate records; its data is loaded only after API authorization.
